# Desktop Locator (sidecar skill)

Default is locate and preview only; **never click without explicit user approval and reliable Windows-side target verification**. Linux has no Windows display / `@oai/sky`; an independent client adapter must obtain screenshots or AX trees from the target Windows window, send them here, and separately decide whether/how to execute any action. Do not treat returned positions as permission to execute.

Use the **absolute script paths supplied by `search_resources`** (not inferred paths):

| Fixed command | Purpose |
| --- | --- |
| `scripts/serve.sh` | Foreground HTTP service, bound to 127.0.0.1 only; stop when finished. Do not launch persistently. |
| `scripts/health.sh` | GET localhost `/health`; fails when service isn't running. |
| `scripts/locate.sh` | Reads one JSON request from stdin; POSTs to localhost `/locate`, prints JSON response. Never accepts a path or opens screenshots from disk. |
| `scripts/workflow.py` | One-shot start → locate → annotated preview → stop, accepts image path and exact target or AX JSON. No clicks; use chat_ai_test Python with Pillow. |
| `scripts/windows_bridge.ps1` | Windows capture with visible cursor; capture, guarded preview, and explicit `execute -ConfirmExecution` mouse move + click. Never run execute without user authorization and a fresh verified target. See WINDOWS_WORKFLOW.md. |

Requires Python 3.10+ and Pillow. Server configured by environment: `DESKTOP_LOCATOR_PORT` (default 18765), `DESKTOP_LOCATOR_VISION_BASE_URL` (default `http://192.168.250.1:18082/v1`), `DESKTOP_LOCATOR_VISION_MODEL` (default `Qwen3.6-35B-A3B`), `DESKTOP_LOCATOR_VISION_API_KEY` (default `EMPTY`). The HTTP service listens only on 127.0.0.1; the model endpoint is outbound and only used for vision requests. The service never captures a display or opens a user-specified file.

`/locate` POST JSON: `{"method":"ax", "selector":{"name":"Save","role":"button"}, "nodes":[{"name":"Save","role":"button","bbox":{"x":10,"y":20,"width":80,"height":30}}],"window_size":{"width":800,"height":600}}` or `{"method":"vision","target":"the Save button", "screenshot_base64":"<base64 PNG/JPEG/WebP>"}`. `method` can be omitted for automatic AX-only when nodes exist (never silently falls back to vision on ambiguity), otherwise vision. AX requests may also include `screenshot_base64`, in which case screenshot dimensions must agree with `window_size` if provided. AX-only requires `window_size`; screenshot requests infer it from the image. Selector name and role must both be exact, case-sensitive, and unique. All bbox values are window-relative pixels and must fit the window. Vision replies contain integer window-relative pixels, `confidence`, `source`, `screenshot_token` (SHA-256 digest of the received encoded screenshot bytes) and `window_size`. AX-only replies have `screenshot_token: null` (no screenshot existed). Clients can compare the token with their own SHA-256 of the decoded screenshot bytes; it is a content hash, NOT a freshness proof or authorization. The client must independently ensure the screenshot still reflects the target window. Errors are JSON with `error` and HTTP 4xx/5xx. No screenshot or image bytes returned to callers.

Limits: max 2 MiB HTTP body, 1 MiB decoded image, 4096x4096 maximum image and 8 million pixels, at most 1000 AX nodes. Vision image is resized to at most 1024x1024 and coordinates mapped back to full window size. Vision output uses strict JSON `{ "bbox_2d": [left, top, right, bottom], "label": "the exact target" }` with bbox coordinates normalized to 0–1000, validated and converted to window-relative pixels. Missing/ambiguous targets should return a null bbox and are rejected; invalid JSON/labels/boxes are rejected. Vision confidence is `null` because this model has no calibrated score. Confidence from the model is self-reported, **not** a calibrated probability; visual grounding can be wrong even when accepted. A real Qwen3.6-35B-A3B probe on a 200x120 synthetic screenshot returned y=420 while reporting confidence=0.95 under the older pixel-coordinate prompt, motivating this switch to normalized bbox_2d; the new approach still requires independent visual verification before any clicks. Caller should verify screenshot freshness and independently handle desktop permissions/scale/offset.

Read `WINDOWS_WORKFLOW.md` before cross-machine capture or Windows actions. Do not try to use Linux Bash to click the remote Windows desktop.

## In-memory task-session service (v1)

Run `scripts/task_serve.sh` **in the foreground**, with project Python (Pillow installed), once per task batch. For a single independent screenshot task, `scripts/task_oneshot.py --image FILE --goal TEXT --window ID [--target TEXT]` automatically starts, observes, plans, finishes and stops its own service (no clicks). It listens only on `127.0.0.1:18766` (`DESKTOP_TASK_PORT` can change the port). `scripts/task_call.sh` is the fixed client; JSON comes on stdin. For a task, POST `start_task` with `{"goal":"describe and locate Save", "window":"win-id", "allowed_actions":["observe","move","click"]}`, retain its `task_id`, then POST `observe` with `{"window":"win-id", "target":"blue Save button", "screenshot_base64":"..."}`. Optional exact AX `selector` and `nodes` also accepted with a screenshot. POST `plan` with `{}`, `verify` with `{"expected":"what success looks like", "new_screenshot_token":"<last hash>"}`, and `action` with `{"action":"move|click","screenshot_token":"...","confirmed":true}` (vision additionally requires a user-reviewed `reviewed_region` with left/top/right/bottom screenshot pixels) (issues **only a validated in-memory handoff**, never sends input), then `finish` / `cancel` with `{}` using `--task-id ID`. Health: `task_call.sh health`.

Service supports up to 32 concurrent independent task sessions, per-task locks, and one serialized model call at a time. Every session (including descriptions, history, IDs) is **RAM only** and is deleted on finish/cancel or process exit; no service-side session files, no durable resume. Limits: 32 observations/session; approximate context admission `DESKTOP_TASK_CONTEXT_TOKENS` (default 8192) accounts for text, image and response reserves. On limit, service returns HTTP 413 `context_limit_exceeded`; no implicit truncation, compaction or partial mutation. This is an explicit conservative estimate, not exact model tokenizer accounting. Images themselves are sent to the model for each observe but not retained in session; observation descriptions and coords stay in memory until close. Avoid sensitive desktop screenshots unless authorized; don't paste them into main chat history.

`observe` describes the image using the existing local vision endpoint and optionally locates a target. `plan` is a conservative deterministic recommendation based on prior observations, and `verify` currently returns **unverified** until human/independent verification—neither is a second autonomous LLM conversation. A task ID is not a chat_ai Agent session; stopping the service clears every active task. `allowed_actions` is a scope declaration, **not an authorization to click**. An action permit binds to the last screenshot token and (for vision) a separately reviewed target rectangle; the Windows action still needs a fresh capture and explicit execution. Windows capture and the guarded action adapter are documented in `WINDOWS_WORKFLOW.md`; never substitute a stale screenshot or inferred AX tree.
